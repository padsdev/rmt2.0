# Experimental Benchmark Workflow

This directory contains the offline, reproducible benchmark workflow for the 17 local Java target projects used in the TCC experimental phase.

## Files

- `benchmark-projects.csv`: manifest of the benchmark inputs.
- `run-benchmark.sh`: runner that uploads each project through the existing RMT API, captures timing data, optionally captures M4 shadow JSONL outputs, and invokes the M5 evaluator when AI shadow mode is active.
- `audit-terminalized-failures.py`: post-run audit utility that scans run logs for terminalized technical failures and exports a CSV report.
- `runs/<run-id>/`: run-specific artifacts generated by the runner.

## Preconditions

- The 17 ZIP projects exist under `target-projects/`.
- The local RMT stack is already running.
- AI integration must match the selected benchmark profile: disabled for `heuristic-only`, enabled in shadow mode for `shadow-stub`, and reserved for future shadow-mode real inference under `shadow-real-model`.
- Redis and LocalStack state should be clean for a fresh benchmark run, or at minimum isolated from previous uploads of the same ZIP files.
- The detection service must receive `RMT_AI_SHADOW_EXPORT_PATH` when AI shadow export is enabled. The application now fails fast instead of silently appending to `target/rmt-ai-shadow-observations.jsonl`.
- The runner allocates a unique shadow JSONL file per benchmark run, truncates it before uploads begin, and acquires a lock so concurrent AI benchmark runs do not share the export stream.

## Candidate universe JSONL (`candidate-universe-v1`)

The detection service may append rows to an **additional** newline-delimited stream when relaxed binding resolves `rmt.ai.candidate-universe-export-path` from the environment (for example `RMT_AI_CANDIDATE_UNIVERSE_EXPORT_PATH`). This exporter does not mutate the legacy M5 shadow JSONL file; it emits one JSON object per line with `schema_version: candidate-universe-v1`.

Each record enumerates a method inspected under every supported heuristic pattern (`STRATEGY`, `TEMPLATE_METHOD`, `FACTORY_METHOD`), merges heuristic-positive labels detected by RMT when available, attaches shadow AI payloads when analyses exist for that heuristic candidate, and tags pattern-aware **hard negatives** using lightweight AST cues. Omitting `RMT_AI_CANDIDATE_UNIVERSE_EXPORT_PATH` keeps the legacy pipeline unchanged—no universe file is written.

Optional metadata: set `RMT_EXPERIMENT_RUN_ID` (`rmt.ai.experiment-run-id`) so append-only runs carrying the same filesystem path remain distinguishable. `project_commit` is intentionally omitted (null); benchmark runners should capture commit hashes in manifests or tooling when needed.

[`run-benchmark.sh`](run-benchmark.sh) accepts `--candidate-universe`: when passed, it creates `experiments/runs/<run-id>/candidate-universe/` and a **staging file** under `detection-and-refactoring/target/runs/<run-id>/candidate-universe.jsonl` (truncated at run start). In Docker, `detection-and-refactoring/target` is mounted at `/shadow-target`, so the detection JVM must use `RMT_AI_CANDIDATE_UNIVERSE_EXPORT_PATH=/shadow-target/runs/<run-id>/candidate-universe.jsonl` (path stays **inside** the bind mount). The runner exports that value plus `RMT_EXPERIMENT_RUN_ID=<run-id>` for operators who restart detection, and records `CANDIDATE_UNIVERSE_EXPORT_PATH` (official run artifact), `CANDIDATE_UNIVERSE_HOST_STAGING_PATH`, and `CANDIDATE_UNIVERSE_CONTAINER_PATH` in `config.env`. After all projects finish, it **copies** the staging file into `experiments/runs/<run-id>/candidate-universe/candidate-universe.jsonl` when staging is non-empty; if staging is empty, the official file stays empty and a **warning** is logged. Any legacy `target/rmt-ai-candidate-universe.jsonl` symlink is removed so nothing points outside the mount.

`RMT_EXPERIMENT_RUN_ID` is read by Spring at **container start**. Changing it per benchmark run still requires `docker compose up -d --force-recreate detection` (or equivalent) with `RMT_EXPERIMENT_RUN_ID` and `RMT_AI_CANDIDATE_UNIVERSE_EXPORT_PATH` aligned to the current run from `config.env`; otherwise `run_id` in JSONL may stay null until the process is recreated with that env.

Later evaluation steps can ingest this corpus to quantify true negatives, specificity, Matthews correlation, balanced accuracy, future threshold sweeps, and ranking-style metrics without perturbing refactoring decisions.

### Offline candidate-universe evaluation (M5 extension)

Legacy M4 shadow JSONL is still evaluated with the original pipeline and filenames (`shadow-evaluation-*.csv` / `.json`). Candidate-universe JSONL is evaluated **separately** when passed to [`rmt-shadow-eval.sh`](/rmt-shadow-eval.sh) via `--candidate-universe-input`. You may pass both `--input` and `--candidate-universe-input` into the same run; outputs land in the same `--output` directory without overwriting shadow artifacts:

- `candidate-universe-integrity.csv`
- `candidate-universe-metrics-overall.csv`
- `candidate-universe-metrics-by-pattern.csv`
- `candidate-universe-ranking-by-pattern.csv`
- `candidate-universe-warnings.md`
- `candidate-universe-threshold-sweep-overall.csv`
- `candidate-universe-threshold-sweep-by-pattern.csv`
- `candidate-universe-threshold-sweep-best.csv`

**Semantics (by design — Slice 2 `ai_label` metrics):** rows with `ai_label=null` are **not** placed in TP/FP/FN/TN in the main universe confusion reports; ranking uses only rows with non-null `ai_score`. Those reports use Slice 2 `NA` semantics (e.g. specificity / MCC withheld when there are no evaluated heuristic negatives **in that report’s sense**).

**Threshold sweep (runs automatically with candidate-universe evaluation):** offline sensitivity analysis using only rows where `ai_score` is **not null**. At each threshold on the grid `0.05, 0.10, …, 0.95` (step `0.05`), a temporary prediction is **`ai_score >= threshold ? 1 : 0`** compared against **`heuristic_label`** as the operational reference. Stored **`ai_label` is not used for sweep predictions**. Rows without `ai_score` are excluded from sweep support counts (`support_scored`). Undefined rates follow the same `NA` conventions as Slice 2 (never write `0` for impossible divisions). Matthews correlation matches the Slice 2 formula; if `support_scored` has zero heuristic positives or zero heuristic negatives, recall/FNR or TN-dependent metrics are `NA`, respectively. **`candidate-universe-threshold-sweep-best.csv`** summarizes, per scope (`OVERALL` then each pattern), the best thresholds by F1, MCC, and balanced accuracy—with explicit `support_scored`, `scored_positives`, and `scored_negatives` context—and **tie-breaking chooses the highest threshold** among tied scores. Best rows are **diagnostic hints for this corpus only**, not evidence of generalization or model superiority vs independent validation. Repeated benchmark orchestration (“run all projects again”) is unchanged; sweeping is an offline evaluator artifact.

**Ranking Precision@k / Recall@k:** for each pattern, scored rows are sorted by descending `ai_score`. Let `effective_k = min(k, number_of_scored_rows_for_that_pattern)`. Then **`precision_at_k` =** (scored heuristic positives in the top `effective_k`) **÷ `effective_k`**. **`recall_at_k` =** that same numerator **÷** (total scored heuristic positives for that pattern)—the recall denominator does not shrink when the pool has fewer than `k` rows.

Java entry point: `br.com.magnus.detectionandrefactoring.ai.experimental.evaluation.ShadowExperimentEvaluationCli` (same classpath as the legacy evaluator). Optional JUnit smoke: `-Drmt.shell.smoke=true` enables a test that invokes `main` with mixed legacy + universe fixtures.

Typical stack startup:

```bash
./rmt.sh all
```

Or, if you prefer local Spring Boot processes:

```bash
./rmt.sh dev
mvn spring-boot:run -pl project-sync-bff
RMT_AI_ENABLED=true RMT_AI_SHADOW_EXPORT_PATH=target/manual-shadow.jsonl mvn spring-boot:run -pl detection-and-refactoring
mvn spring-boot:run -pl metrics-calculator
.venv/bin/python -m uvicorn app.main:app --host 0.0.0.0 --port 8000
```

If you manage the detection service manually, set `RMT_AI_SHADOW_EXPORT_PATH` before starting it. The benchmark runner also exports a run-scoped value and links the legacy host path to that file for compatibility with an already-running local stack.

## Benchmark Profiles

The runner accepts `--experiment-profile` with these values:

- `heuristic-only`: AI disabled. The runner still measures end-to-end project duration, but skips AI health checks and M5 shadow evaluation. Pass `--candidate-universe` to stage exports under `detection-and-refactoring/target/runs/<run-id>/`, copy into `experiments/runs/<run-id>/candidate-universe/candidate-universe.jsonl` after the run, and document `RMT_AI_CANDIDATE_UNIVERSE_EXPORT_PATH` / `RMT_EXPERIMENT_RUN_ID` for the detection service (recreate detection when those env vars change).
- `shadow-stub`: AI enabled in shadow mode using the current stub backend. This is the default runner profile for backward compatibility.
- `shadow-real-model`: reserved for future real GraphCodeBERT inference. The runner treats it like a shadow-mode profile for reporting purposes, but it does not enable or configure the model by itself.
- `shadow-zeroshot`: shadow-mode alias intended for runs where the AI service backend is configured as `graphcodebert`.
- `shadow-finetuned`: shadow-mode alias intended for runs where the AI service backend is configured as `graphcodebert_finetuned`.

The profile is metadata and reporting context for the experiment. It does not toggle decision mode, alter `ProjectStatus`, or change RMT runtime behavior by itself.

## How To Run

Dry run:

```bash
./experiments/run-benchmark.sh --dry-run
```

Dry run with an explicit benchmark profile:

```bash
./experiments/run-benchmark.sh --dry-run --experiment-profile heuristic-only --run-id dry-run-heuristic-only
```

Heuristic-only dry run with candidate-universe export paths prepared:

```bash
./experiments/run-benchmark.sh --dry-run --experiment-profile heuristic-only --candidate-universe --run-id dry-run-heuristic-cu
```

Full benchmark:

```bash
./experiments/run-benchmark.sh --run-id tcc-benchmark-01
```

AI benchmark run with an explicit run-scoped shadow export file:

```bash
./experiments/run-benchmark.sh \
  --experiment-profile shadow-zeroshot \
  --run-id tcc-shadow-zeroshot-01
```

The runner will export:

```bash
RMT_AI_SHADOW_EXPORT_PATH=detection-and-refactoring/target/tcc-shadow-zeroshot-01-shadow.jsonl
```

Threshold / performance experiment with the default profile:

```bash
export RMT_AI_EXPERIMENT_PROFILE=default
./rmt.sh all
./experiments/run-benchmark.sh --run-id tcc-default-profile-01
```

Threshold / performance experiment with a lower Template Method threshold:

```bash
export RMT_AI_EXPERIMENT_PROFILE=low-template-threshold
./rmt.sh all
./experiments/run-benchmark.sh --run-id tcc-low-template-threshold-01
```

Threshold / performance experiment with explicit per-pattern thresholds:

```bash
export RMT_AI_EXPERIMENT_PROFILE=per-pattern-threshold
export RMT_AI_THRESHOLD_TEMPLATE_METHOD=0.10
export RMT_AI_THRESHOLD_STRATEGY=0.55
export RMT_AI_THRESHOLD_FACTORY_METHOD=0.20
./rmt.sh all
./experiments/run-benchmark.sh --run-id tcc-per-pattern-threshold-01
```

Reuse existing compiled evaluator classes:

```bash
./experiments/run-benchmark.sh --run-id tcc-benchmark-01 --skip-eval-build
```

Performance comparison experiment:

1. Run the heuristic-only baseline with AI disabled in the detection service runtime:

```bash
./rmt.sh all
./experiments/run-benchmark.sh \
  --experiment-profile heuristic-only \
  --run-id tcc-heuristic-only-01
```

2. Run the shadow-stub profile with AI enabled in shadow mode using the current stub backend:

```bash
export RMT_AI_EXPERIMENT_PROFILE=default
./rmt.sh all
./experiments/run-benchmark.sh \
  --experiment-profile shadow-stub \
  --compare-with tcc-heuristic-only-01 \
  --run-id tcc-shadow-stub-01
```

The second run writes `performance-comparison.csv`, `performance-overhead-by-project.csv`, and aggregate comparison reports into its run directory.

## Run Output Layout

Each execution creates `experiments/runs/<run-id>/` with:

- `README.md`: run summary with configuration, success/failure counts, and output inventory.
- `config.env`: frozen run configuration for reproducibility.
- `run.log`: global runner log.
- `project-results.csv`: one row per benchmark project.
- `performance-project-summary.csv`: per-project timing summary including total duration, AI duration when available, average AI time per candidate, and candidate count.
- `inputs/benchmark-projects.csv`: manifest snapshot used by that run.
- `logs/<project_id>.log`: per-project upload and polling logs.
- `shadow-jsonl/<runtime-upload-id>.jsonl`: per-project M4 export filtered by runtime `project_id` and deduplicated by `trace_id + entity_id`.
- `candidate-universe/candidate-universe.jsonl` (only when `./experiments/run-benchmark.sh` is invoked with `--candidate-universe`): run-scoped append target for `candidate-universe-v1` JSONL from the detection service.
- `../detection-and-refactoring/target/<run-id>-shadow.jsonl`: run-scoped raw shadow export stream written by the detection service for that benchmark execution.
- `shadow-aggregate.jsonl`: aggregate M4 export rebuilt as the union of all per-project JSONL files.
- `shadow-jsonl-report.txt`: validation report with total records, unique records, unique trace IDs, and duplication rate.
- `evaluation/`: M5 outputs generated by `rmt-shadow-eval.sh`.
- `performance-comparison.csv`: optional cross-run timing comparison generated when `--compare-with` is used.
- `performance-overhead-by-project.csv`: optional per-project overhead report generated when `--compare-with` is used.
- `performance-comparison-summary.json` and `performance-comparison-summary.md`: optional aggregate heuristic-only vs shadow-mode comparison reports generated when `--compare-with` is used.
- `terminalized-failures-audit.csv`: optional audit report generated by `audit-terminalized-failures.py` to separate terminalized technical failures from normal benchmark outcomes.

When available, the shadow JSONL and M5 outputs also include:

- `experiment_profile`
- `template_method_threshold`
- `strategy_threshold`
- `factory_method_threshold`
- `ai_analysis_time_ms`
- `project_processing_time_ms`
- `average_candidate_analysis_time_ms`

If duplication is detected after per-project filtering and deduplication, the runner fails the run and skips M5 evaluation. The run-scoped export file is also recreated empty at benchmark startup, so records from earlier executions cannot accumulate into the current run.

## Terminalized Failure Audit

After a run completes, audit its logs for terminalized technical failures before accepting the experimental results:

```bash
python3 experiments/audit-terminalized-failures.py experiments/runs/<run-id>
```

The script scans `*.log` files recursively, looks for:

- `terminal_reason=FATAL_DETECTION_ERROR`
- `terminal_reason=FATAL_METRICS_ERROR`

It writes `terminalized-failures-audit.csv` inside the run directory, prints a terminal summary, returns exit code `0` when no terminalized failures are found, and returns `2` when one or more occurrences are detected.

For deterministic comparison reports:

- compare runs that use the same `benchmark-projects.csv` manifest snapshot;
- use the same local stack topology between runs;
- generate the comparison from the second run via `--compare-with`.

- `shadow-jsonl/*.jsonl`: raw M4 shadow observations used as the experimental base corpus.
- `evaluation/shadow-evaluation-overall.csv`: overall benchmark agreement/disagreement metrics for Chapter 4 aggregate tables.
- `evaluation/shadow-evaluation-by-project.csv`: per-project breakdown for project-level discussion.
- `evaluation/shadow-evaluation-by-pattern.csv`: pattern-level comparison across Strategy, Factory Method, and Template Method.
- `evaluation/shadow-evaluation-discordant-observations.csv`: disagreement inspection material for qualitative analysis.
- `evaluation/shadow-evaluation-failures.csv`: service and transport failure accounting.
- `README.md` plus `project-results.csv`: execution protocol evidence showing date, configuration, project count, and success/failure status for reproducibility.
